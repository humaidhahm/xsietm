XSIEM · Authorized Home Lab · Architecture & Demo Brief

Two machines, one SIEM pipeline

A Windows endpoint that produces security events, a Linux server that collects, correlates and visualises them, and the cloud architecture patterns that the exact same design maps onto at scale.

1 · The topology

Two virtual machines on a VMware NAT segment (192.168.49.0/24). The Windows host is the monitored target; the Kali VM is both the SIEM server and the attacker used to generate detections. The Windows host reaches the server; the server never reaches into the endpoint.

Data flow: Windows event log → Wazuh agent → manager (TLS enroll, AES events) → OpenSearch index → FastAPI → React dashboard.
Windows 11 Pro · 192.168.49.1

The monitored endpoint

Role: generate the telemetry. It is the thing under surveillance.

  • Windows Security event log (4624 logon, 4625 failed logon, 4728/4732 group changes, 4672 privileged logon)
  • auditpol audit policies must be enabled or no authentication events are produced at all
  • Wazuh agent 4.9.2 (WazuhSvc, auto-start, AES-encrypted channel)
  • Test account xsiem_test — the identity the attacker abuses
  • Inbound firewall opened to 192.168.49.128 only, for RDP/445/22 (RDP itself is enabled, NLA on)
Kali Linux · 192.168.49.128

The SIEM server & adversary

Role: collect, index, analyse, visualise — and play the attacker.

  • Wazuh manager in Docker: authd on 1515 (TLS enrolment), agent channel on 1514 (AES events)
  • OpenSearch indexer storing wazuh-alerts-* indices
  • FastAPI backend on 4000 — the API tier
  • React "SIEM Dashboard" on 3000 — the analyst-facing UI
  • HTTP file server on 8080 — distributes the agent MSI, the CA and the install script
  • Attacker tooling (attack-lab.sh) runs from here against the Windows host

2 · How data actually flows

Nine steps from a keystroke on the endpoint to a row in the teacher's browser. Steps 4 and 5 are the two different transports, and they are deliberately different protocols.

STEP 1
Install & trust The MSI is pulled from the Kali file server. The manager's self-signed CA is imported into Cert:\LocalMachine\Root and copied to the agent folder. The agent is told the manager address, the agent name win-target and the group default via the official MSI properties.
STEP 2
Enable auditing auditpol turns on Logon, Logoff, Other Account Logon Events, Account Lockout, Security Group Management and Other Account Management Events. Without this the agent is connected but silent.
STEP 3
Event generation Windows writes the event to the Security log — a failed logon becomes 4625, adding a user to a group becomes 4732.
STEP 4
Enrolment — TLS, port 1515 The agent opens an outbound TLS connection to the manager's authd and authenticates with the CA it was given. The manager issues a shared key and writes it to client.keys. This is a one-time handshake.
STEP 5
Event shipping — AES, port 1514 For the rest of its life the agent dials out to 1514 and pushes encrypted events on a timer (notify_time=10). No inbound port is ever opened on the endpoint — the endpoint is always the client, never the server.
STEP 6
Normalise & index The manager applies the Wazuh ruleset. A raw 4625 becomes a classified alert with a rule id (60122), a severity, a decoded description and an agent name. Alerts are written to OpenSearch.
STEP 7
Query The FastAPI backend queries OpenSearch and returns JSON: /api/alerts, /api/agents, /api/stats, /health.
STEP 8
Render The React app calls the API and draws the dashboard: severity cards, timeline, donut, live alert table. It talks to http://192.168.49.128:4000 directly.
STEP 9
Respond The analyst (you) sees the detection in the table, clicks through to the Logs/Investigation view, and decides what to do next.
Why two protocols? Step 4 is a sensitive one-time identity handshake and therefore gets full TLS with certificate validation. Step 5 is a firehose of repetitive telemetry and therefore uses a cheap symmetric cipher (AES) with a pre-shared key. This is the same split you see in the cloud: certificate-based mTLS for registration, bulk encrypted channels for the data plane.

Before you present: run the pre-flight

Double-click Xsiem-DemoCheck.cmd on the Windows Desktop (it self-elevates, accept the UAC prompt). It checks every moving part — agent service, enrolment key, live session to 1514, audit policies, event channels, test-account state, leftover artefacts, the XSIEM API, severity coverage and the three attack ports — then prints a green/amber/red checklist. Run Xsiem-DemoCheck.cmd -evidence to also drop a timestamped evidence report on the Desktop that you can attach to your submission.

Two cosmetic quirks in the dashboard, so you are not caught out. The System Status panel in the bottom-left is hardcoded in the React bundle — "Wazuh Manager · Online" and "ELK Stack · Degraded" are static strings, not health checks, and only the agent count is live. So "Degraded" means nothing; it reads that way whether or not the stack is healthy. And the Source IP column currently shows the reporting agent's address (192.168.49.1) rather than the attacker's (192.168.49.128) for remote events — the underlying events and the Wazuh correlation are correct, only the display column is wrong. Both are written up in the project notes.

The architectural lessons to say out loud

  1. Agent-initiated, never inbound. The endpoint dials out; the SIEM never connects in. This is the single most important property in cloud, where endpoints sit in private subnets with no public IP and security groups block unsolicited inbound by default. Your lab already does it correctly — the firewall rules you opened are for inbound test traffic from the attacker, not for the telemetry path.
  2. Decoupled tiers, independently scalable. Manager → indexer → API → UI. In the lab they are four processes on one box. In production they are four autoscaling services, each scaled on its own signal: the manager on connection count, the indexer on ingest volume, the API on query rate, the UI on static-asset caching.
  3. Push vs pull, and why it matters. A pull-based collector (SMTP/syslog receiver) needs the endpoint to be reachable and needs firewall rules on every host. A push-based agent needs one outbound rule per subnet. For a fleet this is the difference between thousands of firewall changes and one.
  4. Certificate-based trust is a platform service. Manually importing a CA here is the equivalent of ACM/Key Vault/cert-manager in the cloud. The failure we actually hit — a manager serving a stock certificate that had expired — is exactly the class of problem that a managed certificate service eliminates, because it renews automatically before expiry.
  5. Normalisation at the collector. Raw 4625 → rule 60122 with severity and description. The ruleset is the detection logic, and it lives server-side so you can update detection rules for thousands of agents by pushing one file, with no agent redeployment. This is the same split as Sigma/Suricata rules living in a central engine.
  6. Immutable event storage plus a query layer. OpenSearch keeps raw events; FastAPI turns them into dashboards and JSON for other tools. In cloud this is the ingest/query split between a durable log store and Athena/BigQuery/Elasticsearch.
  7. API-first so other tools can consume. The React UI is just one client. Because the data is exposed as a clean API, a second frontend, a SOAR playbook, or a ticketing integration can be added without touching the collection pipeline.
  8. Attack-and-defend in one trust boundary. The attacker and the SIEM share a host here, which is fine in a lab but must be separated in production — the attacker tooling would sit in its own isolated network, ideally with egress control so a compromised attacker box cannot reach the SIEM's own management plane. Calling that out is a strong answer to a security question.

5 · Problems solved along the way

Engineering judgement is usually what earns the marks. Be ready to talk about these.

SymptomRoot causeResolution
Agent installed but client.keys empty Manager's authd presented a self-signed certificate that had expired (issued 2024-11-05, valid 1 year). The agent refused it, then the right CA turned out to be a different certificate. Proved it by pointing the agent's server_ca_path at the manager's own cert: the error moved from 18: self-signed to 10: certificate has expired. Regenerated the manager's server cert from the existing CA — no Windows change needed, the agent auto-retried and enrolled within one retry cycle.
Agent connected but produced zero alerts Windows audit policies were not enabled, so no 4625/4732 were ever written. Enabling auditing is a prerequisite, not an optimisation. Enabled six subcategories with auditpol, verified with auditpol /get, and confirmed end-to-end by generating events and watching the rules fire in the dashboard.
OpenSSH capability stuck at InstallPending The server binary and service registration are staged for the next boot. Rebooted, then completed the install via a startup task and confirmed sshd running and automatic.
Manager unreachable after a Windows reboot The Kali VM does not auto-start with the host. Restarted it with vmrun start … nogui. For an unattended lab, enable "start with host" in VMware.
Custom brute-force rule 100100 produced zero alerts despite 21 failed logons It counted on if_matched_sid 60105, but 60105 is the parent of 60122 and never matches terminally — the child consumes the event, so the parent's counter never incremented. The same defect silently kills stock rule 60205. Changed it to count on if_matched_sid 60122, the rule that actually matches terminally, with same_field=win.eventdata.ipAddress. Verified over 20 measured bursts.
The HIGH alert appeared only about four times in five, and which rule won was unpredictable Wazuh 4.9.2 keeps one composite frequency counter per matched event stream. Stock 60204 and custom 100100 both count the same 4625 events, so they compete for that single counter and only one can fire per burst. Proved it with eleven controlled probe rules. Fixed by making 100100 count on the terminal rule id, then suppressing stock 60204 to level 0 so the competition is removed entirely and the HIGH alert is deterministic. Nothing is lost — the MEDIUM tier is covered by 60115, 60109, 60111 and 19004.
Severity filter on the API returned 0 results while the same query with a bigger limit returned 30 The backend applied the severity and search filters in Python after the indexer had already sliced to limit. So ?limit=3&severity=medium looked at the 3 newest alerts, found no medium ones, and returned nothing — silently, with success:true. At one point three of six real HIGH alerts were unreachable through the API. Pushed the filters into the OpenSearch query so they are applied before the limit slice. Verified: /api/stats and /api/alerts?severity= now agree exactly on high, medium and low.
One payload kept reporting "unverified" even though its Wazuh rule was clearly firing The rule matched on a registry-delete pattern that the payload's PowerShell did not use. A probe from the endpoint side using Remove-Item -Path 'HKLM:\…' -Recurse -Force did satisfy the pattern. Aligned the payload's script with the pattern the rule expects, and kept the registry operation in the first script block — the script body captured from an SSH-spawned session appears to be truncated to the first block.
netexec reported "NETBIOS connection timed out" on every failed authentication netexec's failed-auth path does not work against this target; it is not a network problem. Failed-authentication payloads use smbclient / rpcclient, which return a real NT_STATUS_LOGON_FAILURE. netexec is still used for successful authentication.
RDP payloads failed: port 3389 was filtered RDP was disabled at the source on the endpoint — the service was stopped and the registry policy was off. The firewall rule alone was dead weight. Enabled RDP on the endpoint (service automatic, NLA left on) with the inbound rule still scoped to 192.168.49.128 only. Confirmed reachable from Kali, and failed RDP logons produce 4625 like every other protocol.
Agent connected, but only 3 event channels were being collected and only 6 audit subcategories were on — so most attack techniques produced no Windows event to collect Two separate gaps. The agent's ossec.conf only had localfile entries for Application, Security and System. And auditpol had Process Creation, Other Object Access Events and Registry set to No Auditing, so 4688 and 4698 were never written by Windows in the first place. Proved it empirically rather than assuming: probed each technique with auditing off, enabled the three subcategories, added PowerShell/Operational, Defender/Operational and TerminalServices-LocalSessionManager to the agent's localfile list, then re-probed. 4688 (rule 67027), 4698 (rule 60228) and PowerShell 4103/4104 (rule 91813) now flow to the dashboard. The agent's Security query still filters out 4663 and 4670 by design, so those two stay unavailable.

6 · Verification cheat sheet

Account lockout between demo runs. The local policy is threshold 10 / 10 minutes. A burst of 8 failed logons trips the correlation rule (100100, HIGH) without locking the account — 8 is above the correlation threshold and below the lockout threshold of 10. If the payload runs more than once inside the 10-minute observation window the counter keeps climbing and Windows locks the account. Changing the password does not clear a lockout (error 1909). Toggling the account does: net user xsiem_test /active:no then net user xsiem_test /active:yes — verified to unlock immediately. A helper for this is on the Desktop: Reset-XsiemAccount.cmd.

Finding F1 — two correlation rules cannot both fire from the same burst. Wazuh 4.9.2 keeps one composite frequency counter per matched event stream, so every frequency rule counting the same 4625 events competes for that single counter and only one can win. Measured over 20 bursts: 100100 won 16, 60204 won 4, and the winner was non-deterministic. The fix was to count on the terminal-matching rule id (if_matched_sid 60122) rather than on a group, which made 100100 dominant — and then to suppress stock 60204 outright so the competition is removed and the HIGH alert is deterministic. This is the single most interesting thing in the project and it is worth explaining: it is a property of the correlation engine, not a configuration mistake.
