SECTION 1 — WHAT THE PROJECT IS
================================================================================

XSIEM is a complete, working SIEM (Security Information and Event Management)
pipeline built as a two-machine authorised home lab. It is not a simulation and
not a mock-up: a real Wazuh manager collects real Windows security events from
a real Windows endpoint over a real TLS/AES channel, indexes them in
OpenSearch, and serves them through a FastAPI backend to a React dashboard
that an analyst watches in real time.

The project has three moving parts:

  1. A MONITORED ENDPOINT (Windows 11) that produces security telemetry and
     nothing else. It is the "patient".

  2. A COLLECTION AND ANALYSIS STACK (Kali Linux, Docker) that receives the
     telemetry, classifies it with a Wazuh ruleset, indexes it, and presents
     it. It is the "hospital".

  3. AN ADVERSARIAL COMPONENT (the same Kali VM) that generates attacks
     against the endpoint so that detection can be demonstrated and proved
     rather than asserted. It is the "disease".

A menu-driven payload tool on the server side lets an operator request a
specific class of detection on demand — low, medium or high severity — so the
whole pipeline can be exercised live in front of an audience.

The educational point of the project is not "we installed Wazuh". It is that a
SIEM is a one-way data pipeline with a specific trust model, and that making it
correct required understanding and fixing six genuine defects along the way.
Those defects are documented in Section 7 and they are the most valuable
content in the project.

SECTION 3 — DATA FLOW, STEP BY STEP
================================================================================

STEP 1 — INSTALL AND TRUST
  The MSI, the CA and the install script are distributed by a plain-HTTP file
  server on the Kali VM (port 8080) so the endpoint can pull them:
      http://192.168.49.128:8080/wazuh-agent-4.9.2-1.msi
      http://192.168.49.128:8080/rootCA.pem
      http://192.168.49.128:8080/Install-WazuhAgent.ps1
  The manager's self-signed CA is imported into Cert:\LocalMachine\Root and a
  copy is placed at C:\Program Files (x86)\ossec-agent\rootCA.pem, which is
  where the agent's <server_ca_path> points. The agent is told the manager
  address, the agent name and the group through the official MSI properties
  (WAZUH_MANAGER, WAZUH_REGISTRATION_SERVER, WAZUH_REGISTRATION_CA,
  WAZUH_AGENT_NAME, WAZUH_AGENT_GROUP).

STEP 2 — ENABLE AUDITING
  auditpol turns on the subcategories that cause Windows to WRITE the events.
  Without this the agent is connected and silent.

STEP 3 — EVENT GENERATION
  Windows writes to its own event logs. Failed logon = 4625. Adding a user to a
  group = 4732. New process = 4688. Scheduled task = 4698. Service installed =
  7045 (System log).

STEP 4 — ENROLMENT (TLS, TCP 1515) — happens once
  The agent opens an outbound TLS connection to the manager's authd. The
  certificate it presents is validated against the CA it was given. The manager
  issues a shared key and the agent stores it in client.keys. The file holds
  three fields: the agent id, the agent name, and a 64-character hex shared
  key. That key IS the agent's identity to the manager and it is a secret — it
  is gitignored and must never be committed.

STEP 5 — EVENT SHIPPING (AES, TCP 1514) — forever after
  On a timer (notify_time = 10 seconds) the agent dials out to 1514 and pushes
  new events, encrypted with the shared key from step 4. No inbound port is
  ever needed on the endpoint for telemetry.

STEP 6 — NORMALISE AND INDEX
  The manager applies the Wazuh ruleset. A raw 4625 becomes a classified alert
  with a rule id, a level, a severity, a decoded description and an agent name.
  Alerts are written to OpenSearch.

STEP 7 — QUERY
  The FastAPI backend queries OpenSearch and returns JSON:
      GET /health
      GET /api/alerts?limit=&severity=&search=
      GET /api/agents
      GET /api/stats
      POST /api/test-email
  The severity shown in the UI is derived from the Wazuh rule LEVEL, not from
  Wazuh's own severity field: level >= 12 is high, 7 to 11 is medium, below 7
  is low. (This mapping lives in the backend's main.py,
  format_opensearch_alert().)

STEP 8 — RENDER
  The React app calls the backend at http://192.168.49.128:4000 and draws the
  dashboard: severity cards, a timeline, a severity-split donut and a live
  alert table.

STEP 9 — RESPOND
  The analyst sees the detection, opens the Logs or Investigation view, and
  decides what to do.

WHY TWO DIFFERENT PROTOCOLS FOR THE SAME DATA
  Step 4 is a sensitive, one-time identity handshake, so it gets full TLS with
  certificate validation. Step 5 is a repetitive firehose of telemetry, so it
  uses a cheap symmetric cipher (AES) with a pre-shared key. This is the same
  split seen in the cloud: certificate-based mTLS for registration, bulk
  encrypted channels for the data plane.

SECTION 7 — VERIFIED FINDINGS (the engineering content of the project)
================================================================================

F1  TWO CORRELATION RULES CANNOT BOTH FIRE FROM THE SAME BURST
    Wazuh 4.9.2 keeps ONE composite frequency counter per matched event
    stream. Every frequency rule that counts the same 4625 events competes for
    that single counter, so only one can win per burst. Measured over 20
    bursts: the custom rule 100100 won 16 and stock rule 60204 won 4, and the
    winner was non-deterministic. Proven with eleven controlled probe rules
    (100201-100211, all since removed). Consequence: a demo that depends on
    100100 appearing can silently get 60204 instead, and the HIGH beat becomes
    a MEDIUM one. Fix: count on the terminal-matching rule id, then suppress
    stock 60204 so the competition is removed entirely.

F2  if_matched_sid ON A PARENT RULE NEVER FIRES
    The original 100100 counted on if_matched_sid 60105. 60105 is the PARENT of
    60122 and never matches terminally — the child consumes the event, so the
    parent's counter stays at zero. 21 failed logons produced 21 x 60122 and 0
    alerts for 100100. The same defect silently kills stock rule 60205. Fix:
    count on if_matched_sid 60122, the rule that actually matches terminally,
    with same_field=win.eventdata.ipAddress.

F3  THE API APPLIED FILTERS AFTER THE LIMIT SLICE
    /api/alerts applied the severity and search filters in Python AFTER the
    indexer had already sliced to `limit`. So ?limit=3&severity=medium looked
    at the three newest alerts, found no medium ones, and returned nothing —
    silently, with success:true in the body. At one point THREE OF THE SIX real
    HIGH alerts were unreachable through the API. Fix: push the filters into
    the OpenSearch query so they are applied before the limit slice.
    Verified after: /api/stats and /api/alerts?severity= agree exactly on high,
    medium and low.

F4  THE LOCKOUT COUNTER IS CUMULATIVE AND CROSS-PROTOCOL
    The endpoint's policy is threshold 10, duration 10 minutes, observation
    window 10 minutes, and it counts failed logons across SMB, SSH and RDP
    together. While an account is locked, Windows OpenSSH resets the connection
    instead of refusing the password, which reads like a network fault. A
    Windows-side operator can clear it instantly with
        net user xsiem_test /active:no
        net user xsiem_test /active:yes
    (verified — changing the PASSWORD does NOT clear a lockout, it returns
    error 1909 ERROR_ACCOUNT_LOCKED_OUT).

F5  netexec's FAILED-AUTH PATH IS UNUSABLE ON THIS TARGET
    netexec reports "Connection Error: The NETBIOS connection with the remote
    host timed out" for failed authentication. This is not a network problem.
    smbclient and rpcclient return a real NT_STATUS_LOGON_FAILURE and are
    used instead; netexec is still used for successful authentication.

F6  RDP 3389 WAS FILTERED UNTIL THE WINDOWS SIDE OPENED IT
    The firewall rule existed but RDP was disabled at the source — the service
    was stopped and the registry policy was off — so the rule was dead
    weight. After enabling RDP on the endpoint (service automatic, NLA left
    on, inbound still scoped to 192.168.49.128 only), failed RDP
    authentication produces 4625 and successful produces 4624 plus 92657.

TWO MORE DEFECTS FOUND ON THE WINDOWS SIDE
    W  The agent was collecting only 3 event channels and only 6 audit
       subcategories were enabled, so most attack techniques produced NO
       Windows event to collect at all. Enabling Process Creation, Other
       Object Access Events and Registry, plus adding the PowerShell,
       Defender and TerminalServices channels, unlocked 4688 (rule 67027),
       4698 (rule 60228) and PowerShell 4103/4104 (rule 91813).
    W  The manager's authd was serving a stock self-signed certificate that

THE ARCHITECTURAL LESSONS, in the order worth saying them out loud
  1. AGENT-INITIATED, NEVER INBOUND. The endpoint dials out; the SIEM never
     connects in. This is the single most important property in cloud, where
     endpoints sit in private subnets with no public IP and security groups
     block unsolicited inbound by default. The lab already does it correctly —
     the inbound rules that do exist are for the authorised attack traffic, not
     for the telemetry path.
  2. DECOUPLED TIERS, INDEPENDENTLY SCALABLE. Manager, indexer, API and UI are
     four processes on one box here; in production they are four autoscaling
     services, each scaled on its own signal — connections, ingest volume,
     query rate, static-asset caching.
  3. PUSH VERSUS PULL. A pull-based collector (a syslog receiver) needs the
     endpoint to be reachable and needs a firewall rule on every host. A
     push-based agent needs one outbound rule per subnet. For a fleet that is
     the difference between thousands of firewall changes and one.
  4. CERTIFICATE TRUST IS A PLATFORM SERVICE. Importing a CA by hand here is
     the hand-rolled equivalent of ACM / Key Vault / cert-manager. The expired
     manager certificate is exactly the class of problem a managed certificate
     service removes, because it renews before expiry.
  5. NORMALISATION AT THE COLLECTOR. Raw 4625 becomes rule 60122 with a
     severity and a description. The ruleset is the detection logic and it
     lives server-side, so detection rules are updated for thousands of agents
     by pushing one file, with no agent redeployment — the same split as
     central Sigma or Suricata engines.
  6. IMMUTABLE EVENT STORAGE PLUS A QUERY LAYER. OpenSearch keeps the raw
     events; FastAPI turns them into dashboards and JSON for other tools. In
     cloud this is the ingest/query split between a durable log store and
     Athena / BigQuery / Elasticsearch.
  7. API-FIRST, SO OTHER TOOLS CAN CONSUME. The React UI is just one client.
     Because the data is exposed as a clean API, a second frontend, a SOAR
     playbook or a ticketing integration can be added without touching the
     collection pipeline.
  8. ATTACK AND DEFEND MUST BE SEPARATED IN PRODUCTION. The attacker tooling
     and the SIEM share a host here, which is fine in a lab. In production the
     attacker belongs in its own isolated network with egress control, so a
     compromised attacker host cannot reach the SIEM's own management plane.

SECTION 12 — OPEN ITEMS AND KNOWN ISSUES
================================================================================

RESOLVED - all four of the display and noise defects are now fixed and
independently verified against the live index:
  - The Source IP column now shows the event's own source. Across 29 HIGH
    alerts, 27 show 192.168.49.128 (the Kali VM, the real source of the
    remote brute-force alerts) and 2 show "-" (the 60154 Administrators-group
    change, which is a LOCAL action and genuinely has no network source). The
    distinction between a local action and a remote attack is now honest.
  - The raw event body is now mapped into the "log" field and is populated on
    the alerts. The 4103/4104 PowerShell channel and the Security channel
    events are therefore visible in the dashboard's Logs and Investigation
    views instead of being blank.
  - Rule 67027 "A process was created" is suppressed at the ruleset level, so
    the raw 4688 events are still indexed for investigation but no longer
    generate an alert. It went from 96 percent of the last 1000 alerts to
    zero, and the table now shows real detections: 60122 failed logons, 60110,
    60109, 60115, 61102, 61110, 92652, 92657, 19007 and 100100.
  - The dashboard's System Status panel was decorative - "Wazuh Manager:
    Online" and "ELK Stack: Degraded" were hardcoded strings in the React
    bundle rather than health checks, so "Degraded" meant nothing and would
    have read that way even on a perfectly healthy stack. The panel is now
    driven by real state.

STILL OPEN, AND THE ONE THAT MATTERS FOR A LIVE DEMO
  - The F1 competition is now 15 to 1 in favour of the custom rule 100100
    (15 wins against 1 for stock 60204 since the if_matched_sid change), but
    stock 60204 has not been suppressed outright, so roughly one burst in
    sixteen can still produce 60204 instead of 100100. If the teacher triggers
    the brute-force payload once and that burst goes to 60204, the HIGH beat
    silently becomes a MEDIUM one. The safe options are to suppress stock 60204
    to level 0 exactly as 67027 was suppressed, or to run the burst payload
    twice and show the HIGH one.
KNOWN, DOCUMENTED, NOT BUGS
  - "ELK Stack · Degraded" and "Wazuh Manager · Online" in the dashboard's
    System Status panel are HARDCODED STRINGS in the React bundle, not health
    checks. Only the agent count is live. "Degraded" therefore means nothing
    and will read that way regardless of the stack's actual health.
  - Three "PROBE …" alerts remain in the index from the temporary diagnostic
    rules. Removing a rule does not delete the alerts it already produced.
  - 4657 cannot be produced on a standalone workgroup host (see Section 6).
  - 4663 and 4670 are dropped by the agent's own Security-channel query.
  - The Kali VM does not auto-start with the Windows host.
